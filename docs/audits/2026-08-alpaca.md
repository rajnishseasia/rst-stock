# Alpaca copy-trade hardening report

Repo root: `C:/Users/fciaf/OneDrive/Desktop/Projects/rst-stock-site`
Branch: `fix/copy-trade-auto-mirror-hardening` (merge-base `cbcf236`, 6 commits, 20 bugs already fixed)
Scope: Alpaca US equities and options only. Hyperliquid perps are out of scope except where an equity path is handed one.
Threat model assumed throughout: `COPY_TRADE_AUTOMIRROR_ENABLED=true`, `COPY_TRADE_AUTOMIRROR_ALLOW_LIVE=true`, live Alpaca credentials on follows.

15 defects survived double refutation. Two pairs of independently-found reports described the same defect and are merged here (the 403 classification, and the option indicative-feed pricing). Every line number below was re-read at HEAD.

The dominant failure class is not "the mirror places a bad order". It is **the mirror consumes a one-shot exit without placing it**. `stageWindow` advances the discovery checkpoint in the same transaction that inserts the delivery (`copy-mirror.ts:1249-1270`), and `markDeliveryCompleted` / `markDeliveryFailed` are both terminal (`copy-mirror.ts:1303-1318`, `1374-1392`). Nine of the fifteen findings end with a follower holding a position the mirror opened for them, with its only exit instruction already spent and the log line reporting success.

## MUST FIX BEFORE ENABLING

### 1. An ambiguous Alpaca create marks the delivery COMPLETED, so the mirror is never placed and never retried

**What breaks.** `placeMirrorOrder` catches `AlpacaAmbiguousOrderError`, writes the local order row to `SYNCING` with no `brokerOrderId`, and returns the outcome `"syncing"` (`apps/worker/src/services/copy-mirror.ts:4340-4364`). The poll loop treats every returned outcome identically: `const outcome = await this.processCandidate(...)` then `await this.markDeliveryCompleted(row.id, outcome, new Date())` (`copy-mirror.ts:1163-1174`). `completed` is terminal. `loadDueDeliveries` selects only `status = "pending"` (`copy-mirror.ts:1288-1296`), the staging insert is `onConflictDoNothing` on `(followerUserId, sourceItemId)`, and an exhaustive grep of every writer of `copyMirrorDeliveries` confirms nothing ever returns a completed row to pending.

Nothing downstream rescues it. `OrderSyncPoller` "never re-submits" by design (`apps/worker/src/services/order-sync.ts:274-276`), and for a `SYNCING` row with no `brokerOrderId` a 404 from `getOrderByClientId` sets `provenAbsentAtBroker` and spreads `{}`, leaving the row at `SYNCING` rather than returning it to `PENDING`, which is the only marker the resume path reads (`order-sync.ts:439-451`, `copy-mirror.ts:1931`). The row is then re-queried every 30 seconds forever.

The trigger is ordinary, not a rare partition. `isAmbiguousCreateError` classifies 408, 429 and every 5xx as ambiguous (`packages/alpaca/src/client.ts:107-146`), the recovery lookup at `client.ts:349` is the raw SDK call with no `withRetry`, and `retryOn: isAmbiguousCreateError` returns false for the resulting `AlpacaAmbiguousOrderError` itself (no status, no matching code, message does not match the network regex), so `withRetry` throws on attempt 1 and the POST is never retried.

**Concrete failure.** Source T exits AAPL. The worker stages the mirrored closing SELL. Alpaca returns 503 on `POST /v2/orders`, and the immediate `GET /v2/orders:by_client_order_id?client_order_id=rst-copy-<hash>` also fails non-404. `AlpacaAmbiguousOrderError` is thrown with no retry. The order row goes `SYNCING`, the delivery row is written `completed`. No order ever existed at Alpaca. `OrderSyncPoller` gets a 404, concludes "proven absent", and leaves the row `SYNCING` forever. The follower keeps the full mirrored AAPL long that the mirror opened, its only exit instruction consumed, every log line reporting the delivery as completed.

**Vendor doc violated.** `docs.alpaca.markets/reference/getorderbyclientorderid` documents `GET /v2/orders:by_client_order_id`, "Retrieves a single order specified by the client order ID", which is precisely the recovery Alpaca provides for an uncertain create and which this path declines to re-drive. `alpaca.markets/support/usage-limit-api-calls` documents the 200 requests-per-minute limit returning `429 - Too Many Requests`, a refusal, not an unknown outcome.

**Fix.** Make `"syncing"` non-terminal. Either return the delivery to `pending` with a backoff instead of calling `markDeliveryCompleted`, or throw `EAGAIN` from the ambiguous branch so the existing transient path requeues it (the file already uses this pattern in roughly fifteen places). Separately, wrap the `getOrderByClientId` recovery lookup at `client.ts:349` in `withRetry` with a short backoff so a single correlated failure on both calls does not manufacture the ambiguous error in the first place.

Internal contradiction worth noting for the fixer: `classifyMirrorFailure` already classifies 408/409/425/429/5xx as **transient** (`copy-mirror.ts:529-540`). The ambiguous branch intercepts before that classification runs and retires the intent instead.

### 2. HTTP 403 is classified permanent, so a wash-trade or insufficient-shares rejection destroys a mirrored CLOSE on attempt 1

Two independent lenses found this at `copy-mirror.ts:529` and `:535`. Same defect.

**What breaks.** `classifyMirrorFailure`'s transient predicate admits only status 408, 409, 425, 429 and `>= 500` (`copy-mirror.ts:529-540`, re-read and confirmed verbatim). Everything else, 403 included, falls through to `kind: "permanent"`. `placeMirrorOrder` then writes the order row `status: "REJECTED"` (`copy-mirror.ts:4366-4377`) and rethrows. `markDeliveryFailed` exempts a close from the **attempt ceiling** only, and only for transient failures: `const exhausted = hasExhaustedDeliveryAttempts(attempts) && !closingDelivery;` (`copy-mirror.ts:1354`), with the write at `1373-1392` sending any permanent failure straight to `permanent_failure`. Its own comment says so: "Permanent failures still terminate here whatever the intent is."

403 at Alpaca is not a property of the request. It is the wash-trade refusal, which is a statement about **another order the same account currently has open**, and it clears by itself the moment that order fills or is cancelled. The equity mirror submits a plain `market` order (`copy-mirror.ts:4226-4243`) and never inspects the follower's open orders; the only `client.getOrders` call in the file is the duplicate-recovery scan at `4211`, gated on `!insertedOrder`. `withRetry` does not help either: `retryOn` is `isAmbiguousCreateError`, and 403 is not ambiguous.

Recovery is impossible even if something requeued it. The close-revival branch at `copy-mirror.ts:1534-1546` is gated on `status === "CANCELLED" && assetType === "PERP" && perpReduceOnly === true`, so a `REJECTED` equity row falls through to the duplicate short-circuit at `4183` and the delivery is marked completed having placed nothing.

**Concrete failure.** A follower holds 100 MSFT that the mirror opened, and separately leaves an ordinary resting GTC limit BUY for 10 MSFT. The source closes MSFT. The mirror submits `{symbol:"MSFT", qty:100, side:"sell", type:"market", time_in_force:"day"}`. Alpaca's wash-trade matrix row `limit buy` + `market sell` = "always rejected" fires, returning 403 (the axios-based SDK surfaces it as `error.response.status === 403`, which `errorStatus` at `copy-mirror.ts:451-462` reads). Order row `REJECTED`, delivery `permanent_failure`, attempt 1. The follower keeps 100 MSFT with their single mirrored exit spent, and cancelling the interfering order minutes later recovers nothing.

**Vendor doc violated.** `docs.alpaca.markets/docs/user-protection`: "If we determine that an order could result in a wash trade, we trigger our protection measures, reject the order, and send back an error message with the HTTP status code 403 (Forbidden)." The rejection table lists `limit buy` + `market sell` and `limit sell` + `market buy` as **always rejected**, unconditionally and price-independently, with only bracket/OCO and trailing-stop orders excepted. It applies to paper accounts too. Alpaca also returns 403 for "Buying power or shares is not sufficient", another condition defined by other account state that resolves on its own.

**Fix.** Do not blanket-flip 403 to transient: 403 is overloaded at Alpaca and also covers "account is not authorized to trade", which this repo already correctly treats as permanent (`apps/api/src/lib/alpaca-credential-check.ts:117`). Discriminate on the response body message. Treat wash-trade (`40310000`) and insufficient-shares/buying-power 403s as transient so the close is retried past the ceiling, and add a pre-flight `getOrders(status:"open", symbols:[symbol])` check on the mirror path so an opposing resting order is either cancelled first or the close deferred with `EAGAIN`.

### 3. Adding a Live Alpaca account overwrites the Paper credential row in place, re-pointing every armed follow at real money

**What breaks.** `saveApiCredentials` finds the existing row with `and(userId, provider, input.accountId ? eq(accountId, input.accountId) : isNull(accountId))` (`apps/api/src/routers/user-settings.ts:66-75`) and then UPDATEs that row's `accountType` (`:85`), `username` and `encryptedAccessToken` on the same `user_api_credentials.id`. The shipped UI never sends `accountId`: `buildSaveBrokerCredentialsInput` returns only `{provider, accountType, accessToken, username}` (`apps/web-v2/src/lib/broker-credentials-form.ts:16-21`, pinned by its own test "omits accountId from the frontend save payload"), and every Alpaca row is written `accountId: input.accountId || null` (`user-settings.ts:81`, `:101`). So the `isNull` branch always matches the user's one Alpaca row, and the "Add Broker Account" form, sitting under a plural "Connected Accounts" list, is a destructive in-place overwrite.

Nothing else notices. `copy_trade_follows.credential_id` is unchanged and has no `accountType` column, `auto_mirror` stays true, the frozen delivery candidate carries no paper/live marker, and `decideFollowConsent` re-validates by comparing credential UUIDs only (`apps/worker/src/services/copy-mirror-consent.ts:243-251`). `checkAlpacaCredentials` even parses `account_number` off `GET /v2/account` (`apps/api/src/lib/alpaca-credential-check.ts:99-112`) and the router discards it.

Note the asymmetry: **deleting** a credential is fail-safe, because `copy_trade_follows.credential_id` is `onDelete: "set null"` and consent then hits the empty-credential branch. **Updating** one is fail-open.

**Concrete failure.** A follower connects Alpaca PAPER keys (row X) and arms a follow against X. Weeks later they open Settings, pick Account Type = Live, paste their live key pair and save. `checkAlpacaCredentials` verifies against `api.alpaca.markets` and passes; row X becomes `accountType=LIVE` with the live secret on the same UUID. The follow still points at X with `autoMirror=true`. Next poll: consent sees the same UUID and returns proceed; `copy-mirror.ts:1902` computes `isPaper = isPaperAccount("LIVE") = false`; the `!c.isPaper && !liveAllowed` gate at `:768` does not fire; `new AlpacaClient({paper:false})` targets `api.alpaca.markets` and a real-money market order is placed. In-flight `PENDING` mirror rows sized against the paper account are resumed onto the live account by `copy-mirror.ts:1931-2124`. The toast says "Credentials saved successfully!".

**Vendor doc violated.** `docs.alpaca.markets/docs/paper-trading`: "Your paper trading account will have a different API key from your live account", with paper reached at `https://paper-api.alpaca.markets` and live at `https://api.alpaca.markets`. Alpaca treats paper and live as two distinct accounts with distinct credentials. Collapsing both into one credential row means the UUID stored on the follow no longer identifies an account, so the identifier the consent gate depends on is not stable across the exact thing it exists to protect.

**Fix.** Include `accountType` in the existing-row lookup key so paper and live become separate rows (the schema already expects this: `packages/db/src/schema/user-credentials.ts:58-65` documents the hyperliquid unique index as deliberately partial so "multi-account providers (e.g. alpaca paper + live rows) keep their existing many-rows-per-user shape"). Persist the `account_number` the credential check already fetches into `account_id`. If an in-place overwrite must remain possible, refuse it while any armed follow references the row, or require the repoint confirmation that `apps/web-v2/src/components/copy-trade/mirror-consent.ts:60-77` already implements for the account picker.

### 4. An option closed from the Positions panel can never be mirrored, so the follower's mirrored contract has no exit

**What breaks.** `positions.close` writes the OPTION close row as `symbol: input.symbol` (the OCC contract symbol, e.g. `AAPL260821C00255000`), `assetType: "OPTION"`, `tradeAction: "Sell"`, with `optionExpiration`/`optionStrike`/`optionType` left NULL (`apps/api/src/routers/positions.ts:481-495`, re-read; the option-ness is already known at `:462`). `publishClose` republishes that OCC symbol to `social_trades` (`positions.ts:402-417`). Copy-mirror discovery requires an OPTION row to carry a `BuyToOpen`/`SellToClose` action plus all three contract fields (`apps/worker/src/services/copy-mirror-candidate-sources.ts:507-520`, with `optionTradeAction` at `:170-172` accepting only those two), so the row is dropped as `missing-option-contract`.

The **open** path is asymmetric: `orders.submitOrder` stores the UNDERLYING in `symbol` plus full contract identity (`apps/api/src/routers/orders.ts:695-706`), and mirrors correctly. The Positions panel renders a Close button for every row including `us_option` and passes `position.symbol` verbatim (`apps/web-v2/src/components/trade/positions-panel.tsx:582-614`), so this is the default exit UX, not an obscure endpoint.

Widening `optionTradeAction` to accept `"Sell"` would not fix it: `mirroredEquityExposure` matches `orders.symbol = cand.symbol` (`copy-mirror.ts:3020`, whose own comment states "OPTION rows carry the UNDERLYING in `symbol`"), so an OCC-symbol close resolves to `no-mirrored-exposure` instead.

**Concrete failure.** A source with `shareTrades` on buys 2x AAPL 260821 C255 through the order ticket. Discovery stages it and the follower's mirror buys the contract. The source exits by pressing Close on the Positions panel. Discovery logs `skip: missing-option-contract` and drops it; `stageWindow` advances the checkpoint either way. The follower is left long a decaying contract with the source flat, and no mirrored exit will ever exist. `placeMirrorOrder` attaches no exit plan to a mirrored option, so there is no protective order either. Second order effect: leaderboard FIFO buckets options on `(userId, symbol, optionExpiration, optionStrike, optionType)` (`apps/api/src/routers/leaderboard.ts:584`), so these closes never pair with their opens and the trader's realized option P&L and closed-trade count stay at zero on the surface followers use to pick who to copy.

**Vendor doc violated.** `docs.alpaca.markets/reference/postorder` confirms an option order's `symbol` is the OCC contract symbol (examples `AAPL250620C00100000`) and that `position_intent` is `{buy_to_open, buy_to_close, sell_to_open, sell_to_close}` with `sell_to_close` = "exits an existing long position". `docs.alpaca.markets/docs/options-trading` confirms positions reuse the existing Positions API model keyed by OCC symbol, which is why `close()` receives an OCC symbol where `submitOrder` receives an underlying. The two representations are not interchangeable and the repo stores both in one column with no discriminator.

**Fix.** In `positions.close`, when `closeAssetType === "OPTION"`, parse the OCC symbol and persist the underlying in `symbol` plus the three contract columns, and write `tradeAction: "SellToClose"` (or `"BuyToClose"` for a short). That makes the close row byte-identical in shape to the one `orders.submitOrder` produces, which discovery, `mirroredEquityExposure` and the leaderboard all already handle. Also audit `positions.ts:663` (`closeAll`), which hardcodes `assetType: "EQUITY"` while publishing an order symbol that for an option is the OCC symbol, sending an OCC ticker down the equity path.

### 5. `closeAll` publishes a social trade for every element of Alpaca's 207 body, including positions the broker refused to close

**What breaks.** `positions.closeAll` treats the return of `client.closeAllPositions` as `AlpacaOrder[]` (the wrapper asserts that type at `packages/alpaca/src/client.ts:309`, which compiles only because `private alpaca: any` at `:196`). `DELETE /v2/positions` actually returns HTTP 207 with an array of `{symbol, status, body}` envelopes, and the SDK passes `resp.data` through unchanged (`dist/api.js` `sendRequest`, `dist/resources/position.js` `closeAll`). 207 is a 2xx, so axios resolves and nothing notices. The publish loop at `apps/api/src/routers/positions.ts:661-673` reads `order.side`, `order.qty` and `order.id` off the **envelope**, where they do not exist (the real order is under `.body`), and never reads `order.status`. Result: one `social_trades` row per position with `side="sell"` (the `|| "sell"` fallback), `qty=1` (the `? : 1` fallback), `assetType` hardcoded `"EQUITY"`, and `brokerOrderId` undefined, which inserts as NULL because the column is nullable (`packages/db/src/schema/social-trades.ts:29`). The handler then returns `success: true, "All positions closed"` regardless of per-element status.

Those rows are exactly what discovery selects. `findMirrorCandidates` LEFT-joins orders on `socialTrades.brokerOrderId` (`copy-mirror-candidate-sources.ts:311-316`), so NULL simply fails to join; the mirror-origin guard at `:372` reads the joined `clientOrderId`, which is NULL and passes; and because side is `"sell"` the candidate is a closing intent, exempt from the source-fill gate (`copy-mirror.ts:1857`) and from the consent and staleness gates (`:1802-1806`).

**Concrete failure.** Source T holds AAPL, MSFT and NVDA. `closeAll` is invoked. Alpaca cannot liquidate MSFT because a resting sell holds the shares, so the body is `[{symbol:"AAPL",status:200,body:{...}}, {symbol:"MSFT",status:403,body:{...}}, {symbol:"NVDA",status:200,body:{...}}]`. Three `social_trades` rows are published, MSFT included. On the next poll, every follower with mirrored MSFT exposure is staged a closing SELL and `placeMirrorOrder` submits a real market sell for a close the source never made. T's MSFT position is still open and the API told them otherwise. The successful elements are corrupted too: `qty=1` and `brokerOrderId` NULL on every one.

**Vendor doc violated.** `docs.alpaca.markets/reference/deleteallopenpositions-1`: the response is 207 Multi-Status carrying an array of `PositionClosedReponse`, required fields `symbol` and `status` ("HTTP status code for the attempt to close this position"), with `body` an optional `$ref` to Order.

**Fix.** Type `closeAllPositions` as `Array<{symbol: string; status: number; body?: AlpacaOrder}>`, publish only elements where `status` is 2xx, read side/qty/id off `.body`, and return a per-symbol result instead of an unconditional `success: true`.

**Reachability note (from verification).** No shipped UI calls `positions.closeAll`. The "Close all (market)" button at `apps/web-v2/src/components/trade/close-position-modal.tsx:274` is a full-size close of one position on `positions.close`. `closeAll` is a mounted `protectedProcedure` callable by any authenticated client, so it is live surface, but the "trader clicks Close all" narrative overstates in-app reachability.

### 6. An unsettled mirrored BUY counts toward the attribution ceiling at its REQUESTED size, so a mirrored close can liquidate the follower's own shares

**What breaks.** `mirroredEquityRowQty` returns the requested `quantity` for any mirror row that has not settled: only CANCELLED/REJECTED/EXPIRED return 0, a PENDING/SYNCING/SUBMITTED row falls to `return requested` (`copy-mirror.ts:923-937`), and a still-working PARTIAL returns `Math.max(executed, requested)` at `:931-933`. `netMirroredEquityQty` sums those into `exposure.qty`, which becomes `mirroredLongQty` and is the **only** attribution ceiling on a mirrored SELL (`clampSellToMirroredExposure`, `copy-mirror.ts:980-994`). `mirroredEquityExposure` applies no status filter to the rows it nets (`:3032-3044`).

The comment at `copy-mirror.ts:915-921` defends the over-read with "the live-position clamp still applies on top". That clamp is `decideSellMirrorQty`, which bounds the sell to `Math.floor(heldLongQty)` from `fetchLongQty`, i.e. the account's entire long including shares the follower bought themselves (`copy-mirror.ts:877-885`, `3939-3949`). The two clamps therefore do not compose into an attribution bound.

The perp path answers the identical question correctly: `pairedOpenOutcomeAmbiguous` (`copy-mirror.ts:2822-2856`) makes a close DEFER when the paired open sits at PENDING/SUBMITTED/PARTIAL, but it is hard-scoped to `venue = hyperliquid` and `assetType = PERP`. `holdEquityCloseIfPairedOpenQueued` fires only on the `no-long-position` / `no-mirrored-exposure` skips, so it is never reached when the follower holds their own shares.

**Concrete failure.** A follower owns 500 XYZ they bought themselves. A mirrored BUY for 100 XYZ is submitted at 19:30 ET; Alpaca queues the day order for the next session, so it sits open with `filled_qty = 0` and the local row is SUBMITTED (`order-sync.ts:200-221` maps `new`/`accepted`/`done_for_day` to SUBMITTED). The source close arrives. `mirroredLongQty = 100` (a request, not a holding), `fetchLongQty` returns 500 (the follower's own shares), `decideSellMirrorQty(100, 500) -> 100`, `clampSellToMirroredExposure(100, 100) -> 100`. The mirror sells 100 of the follower's own shares. If the queued BUY is then rejected at release for buying power or a halt, the follower is permanently 100 shares short of a position the mirror never opened. The in-hours variant needs no after-hours conditions at all: `placeMirrorOrder` inserts the row PENDING **before** the broker call (`:4145-4175`), and a transient createOrder failure leaves it PENDING at full requested size.

**Vendor doc violated.** `docs.alpaca.markets/docs/orders-at-alpaca`: an order in `new`/`accepted`/`partially_filled` has moved only `filled_qty` shares, and "orders not eligible for extended hours submitted after 4:00pm ET will be queued up for release the next trading day". `qty` on an order is a request; `qty`/`qty_available` on the position are what the account holds.

**Fix.** Count only `executedQuantity` toward mirrored exposure, and when any mirror row for the symbol is unsettled, return `unanswerable` from `mirroredEquityExposure` so the caller throws `EAGAIN` and defers, exactly as the perp path does and as this file already does at `:1637-1660`. Deferring places no order and costs only reconciler latency.

**Note.** `apps/worker/src/services/__tests__/copy-mirror-sell-attribution.test.ts:391-407` currently pins this behaviour as intended (SUBMITTED open of 30, `executedQuantity` null, live long 500, asserts a sell of 30 is placed). That test needs to change with the fix.

### 7. Equity mirror orders carry no `position_intent`, so a mirrored open silently covers the follower's own short and corrupts the exposure ledger

**What breaks.** `placeMirrorOrder` builds the order request with symbol/qty/side/type/time_in_force/client_order_id only (`copy-mirror.ts:4227-4243`). `position_intent` is attached exclusively inside `if (params.assetType === "OPTION")` at `:4244-4250`. Every equity mirror, open and close, reaches Alpaca with the field absent. The BUY path never reads the follower's position at all: `getPosition` is called from exactly one place in the whole worker, `fetchLongQty` (`:3939-3948`), reached only under `if (cand.side === "sell")` (`:1951`, `:2308`), and `mirroredLongQty` is hardcoded to 0 for opens (`:2209`). Downstream, `mirroredEquityRowQty`/`netMirroredEquityQty` credit every filled mirror BUY as `+qty` of mirrored LONG with no check that a long actually resulted, signed only by the trade-action verb (`:905-965`). `mirroredEquityExposure` applies no time window (cap 5000 rows), so the phantom credit is permanent.

`apps/api/src/routers/orders.ts:752-768` already maps all four intent values, but only when `input.assetType === "OPTION"`.

**Concrete failure.** A follower is short 100 TSLA from their own trading on a live margin account. The source buys TSLA. The mirror sizes 30 and POSTs `{symbol:TSLA, qty:30, side:buy, type:market, time_in_force:day}` with no intent. Alpaca cannot hold a long and a short in the same symbol, so the buy covers 30 of the follower's short: a background worker cuts their deliberate exposure by 30% and realizes P&L they never asked to realize, with no guard and no log. The ledger now records +30 of mirrored long that does not exist. Later the follower covers and goes long 200 TSLA of their own; the source round-trips TSLA, the mirror opens +25, and the next source close sizes from `30 + 25 = 55`, passes `decideSellMirrorQty(55, 225)` and `clampSellToMirroredExposure(55, 55)`, and sells 55 shares, 30 of which are the follower's own. That is the exact invariant the attribution clamp added in `ffc3e02` exists to protect: the clamp is intact, its input is poisoned.

**Vendor doc violated.** `docs.alpaca.markets/reference/postorder` defines `position_intent` ("Represents the desired position strategy") on `CreateOrderRequest`, the equity single-order schema, with `buy_to_open` and `sell_to_close` among its four values. `alpaca.markets/learn/how-to-fix-common-trading-api-errors-at-alpaca`: "Alpaca does not support holding long and short positions in the same symbol at the same time." Declaring an intent that conflicts with account state is rejected server-side with 422 / `40010001` "position intent mismatch. inferred sell to close", which is the broker-side backstop the equity mirror declines to use.

**Fix.** Two changes, both needed. (a) Send `position_intent` on equity mirrors: `buy_to_open` / `sell_to_close` for the normal mirror direction, so Alpaca rejects a mismatch rather than silently netting. Note the caveat found in verification: because Alpaca cannot hold both sides, the intent will cause a **rejection**, not a second position, which is the desired fail-closed outcome and turns the phantom credit into a `REJECTED` row worth 0. (b) Read the follower's position before a mirrored BUY, the same way the SELL path already does, and skip or defer when the account is short the symbol. Relying on the ledger's assumption that a filled BUY produced an equivalent new long is the root defect.

### 8. A long fully reserved by open orders reads as "no long position", and the one-shot exit is consumed rather than deferred

**What breaks.** `fetchLongQty` returns `Math.floor(Number(pos.qty_available ?? pos.qty))` and reports 0 when `qty_available` is 0 (`copy-mirror.ts:3939-3949`). `qty_available` is the position size minus shares tied up in open orders, so a position that fully exists but is entirely reserved by a resting sell is indistinguishable from one that does not exist. The `??` never rescues it: `packages/alpaca/src/types.ts:77` declares `qty_available: string` as required, Alpaca sends `"0"`, which is not nullish, and `packages/alpaca/src/client.ts:263` is a bare passthrough with no normalization.

`decideSellMirrorQty(placeQty, 0)` then returns `{action:"skip", reason:"no-long-position"}` (`:877-885`), `holdEquityCloseIfPairedOpenQueued` defers only when a paired OPEN is still in the pending delivery queue, and `processCandidate` returns `"no-long-position"`, which the poll loop at `:1174` turns into `markDeliveryCompleted`. Terminal.

The reserving order is placed by this product's own API: `submitBracket` (`orders.ts:1006`), `submitWithExitPlan` (`:1197`), `submitOCO` (`:1452`), `submitTrailingStop` (`:1658`), all with `timeInForce` defaulting to `"gtc"`.

**Concrete failure.** The mirror opened 200 MSFT for a follower. The follower attaches a GTC stop-loss covering all 200 shares. `GET /v2/positions/MSFT` returns `qty=200, qty_available=0`. The source closes MSFT. `mirroredEquityExposure` is DB-derived and correctly yields 200, so `placeQty=200`, but `fetchLongQty` returns 0, the candidate skips with `no-long-position`, no paired open is queued so nothing defers, and the delivery is marked completed with an audit line recording `heldLongQty: 0` while the account holds 200 shares. The follower later cancels the stop and is stranded long 200 MSFT in a trade the source is fully out of. Partial reservation is worse because it is silent: a stop on 100 of 200 shares yields `qty_available=100`, the exit is clamped to a partial close, and the remainder is completed as a success.

**Vendor doc violated.** `docs.alpaca.markets/reference/getopenposition-1` defines `qty` as "The number of shares" and `qty_available` as "Total number of shares available minus open orders / locked for options covered call". `alpaca.markets/learn/how-to-fix-common-trading-api-errors-at-alpaca`: "When you submit a sell order (e.g., a Limit Sell or Stop Loss), the shares tied to that order are reserved until the order is filled or canceled." A zero `qty_available` is evidence of reservation, not absence.

**Fix.** Distinguish the three cases. When `getPosition` 404s, the account is genuinely flat and completing is correct. When `qty > 0` but `qty_available === 0` (or is less than `placeQty`), either cancel the reserving orders on that symbol and then sell, or throw `EAGAIN` and defer, which is what the neighbouring hold-backs at `:1651-1657`, `:2278-2283` and `:2944-2951` already do for this class of ambiguity. Do not simply switch to `pos.qty`: Alpaca would reject the sell for insufficient available quantity, which is still better than silently spending the exit but is not the fix.

**Note.** Every position fixture in `apps/worker/src/services/__tests__/` sets `qty_available` equal to `qty` (13 distinct pairs), so no existing test can distinguish the two reads. `apps/api/src/routers/positions.ts:459-467` already reads them separately and raises "No available quantity to close", so the distinction is understood elsewhere in the repo.

### 13. Ratio sizing copies the source's REQUESTED share count, not what actually filled

**What breaks.** Discovery sets `sourceQty = trade.orderQuantity ?? trade.socialQty` under a comment asserting "orders.quantity is the authoritative number of shares/contracts that actually traded" (`apps/worker/src/services/copy-mirror-candidate-sources.ts:527-533`). It is not. `orders.quantity` is written once at submission from the requested size (`apps/api/src/routers/orders.ts:695`) and the reconciler never updates it: `order-sync.ts:357-370` writes `executedQuantity`, `executedPrice`, `executedAt` and `status`, and an enumeration of every `update(schema.orders)` call site in the repo confirms no path rewrites an in-app source order's `quantity`. `socialTrades.qty` is the same requested number (`orders.ts:789`). So `ratio` mode computes `floor(ratio * requestedQty)` (`apps/api/src/lib/copy-mirror.ts:87-101`) against a number that can be many times the position the source actually holds.

The fill gate added in `ef4bda2` does not help: `classifySourceOrderExecution` returns "executed" as soon as `executedQuantity > 0` (`copy-mirror.ts:413-426`), so a heavily partial fill passes through, and the true fill it read is then discarded for the frozen candidate value.

The perp branch of the very same function does it correctly at `copy-mirror-candidate-sources.ts:395` (`orderExecutedSizeDecimal ?? orderQuantityDecimal`). The repo also states the correct rule against itself at `external-fill-sync.ts:299-307`: "copy-mirror sizes off `quantity`, and an order that was canceled after filling 20 of 500 shares must not fan out as a 500-share mirror." Orders placed through the app get the opposite treatment.

**Concrete failure.** A source requests 200 shares of a $4 name as a DAY limit; 40 fill and the remainder is cancelled at the close. `orders.quantity = 200`, `executedQuantity = 40`, status CANCELLED. The gate says "executed", discovery hands the candidate `sourceQty = 200`, and a follower on `ratio: 1` buys 200 shares ($800, under the $1,000 per-order cap) for a position the source ended at 40. Worse on the way out: `sizeExitFromMirroredPosition` excludes ratio mode (`copy-mirror.ts:2213`), so the mirrored exit is also `ratio * sourceExitQty = 40`, leaving the follower permanently holding 160 shares of a position the source is fully out of.

**Vendor doc violated.** `docs.alpaca.markets/reference/getallorders-1` defines `qty` as "Ordered quantity" and `filled_qty` as "Filled quantity", two separate fields, with `qty` never rewritten to the fill. `docs.alpaca.markets/docs/orders-at-alpaca` confirms `canceled` and `expired` are terminal and that DAY orders are automatically canceled after the closing auction, so a partially-filled DAY limit ends terminal with `filled_qty < qty`.

**Fix.** Select `orders.executedQuantity` in discovery and prefer it, mirroring the perp branch at `:395`. Better still, use the `executedQuantity` already re-read for the fill gate at `copy-mirror.ts:1859` for ratio sizing, since the fill can grow between staging and execution.

**Severity note.** One verifier held high, one corrected to medium on the grounds that it bites only in `ratio` mode (default is `pct`) and each occurrence is bounded by `DEFAULT_MIRROR_MAX_ORDER_DOLLARS = 1000`. Above that price the oversized mirror becomes a silent `dollar-cap` skip, which is a different wrong outcome rather than a safe one.

### 14. A fractional source fill is recorded and republished as at least one whole share

**What breaks.** `buildExternalOrderRow` collapses a fractional fill into `Math.max(1, Math.round(quantityBasis))` because `orders.quantity` is a NOT NULL integer (`external-fill-sync.ts:305-310`; `packages/db/src/schema/orders.ts:142`). The same transaction republishes it with `qty = Math.max(1, Math.round(...))` into `social_trades`, whose `qty` is also an integer (`external-fill-sync.ts:721-733`, repeated at `:837`). **Concrete failure.** A followed trader buys $18 of a $900 stock in the Alpaca app: a notional order filling 0.02 shares. The poller records `quantity = 1` and publishes `social_trades.qty = 1`. **Reachability note.** The whole ingest is behind `EXTERNAL_FILL_DETECT_ENABLED === "true"` (`external-fill-sync.ts:412`), which ships inert. `docs/deployment/copy-mirror-env-reference.md:135` prescribes `true` for a copy-trading deployment, which is the configuration in this threat model. Only `ratio` sizing reads `sourceQty`; `pct`/`pct_equity`/`usd` are unaffected.

### 15. Mirrored option limit prices come from the free indicative feed and are then rested GTC with no re-price and no cancel

Two independent lenses found this at `packages/alpaca/src/client.ts:919`. Same defect, merged.

**What breaks.** `getLatestOptionQuote` hardcodes `&feed=indicative` in the URL with no caller override (`client.ts:919`; a repo-wide grep for `opra|indicative` returns only this line, the sibling chain-snapshot call at `:893`, and its comment at `:888`). `fetchOptionPrice` takes the raw `bp` for a sell or `ap` for a buy off that quote (`copy-mirror.ts:3991-4007`), and that exact number is both the sizing price for the 100x notional and the actual `limit_price` on the real order (`copy-mirror.ts:2416`, submitted at `:4246`). **Concrete failure.** The source publishes a SellToClose on 3 contracts. (c) Either stop making option exits GTC by default, or add a re-price/cancel pass in `order-sync` so an unfilled mirrored exit is chased rather than abandoned, and do not zero mirrored exposure on the basis of an unfilled sell (see finding 6, same root).

Repeat clicks with the same idempotency key are answered locally with "Close outcome is still syncing with Alpaca" without contacting the broker until the intent fingerprint rotates or the page reloads.

**Vendor doc violated.** `docs.alpaca.markets/reference/deleteopenposition-1` lists exactly two query parameters, `qty` and `percentage`, and no `client_order_id`; it "Returns the order created to close out this position" with Alpaca's own auto-generated client id. `POST /v2/orders` is the only endpoint that accepts a caller-supplied `client_order_id`.

**Fix.** Do not write a fabricated `brokerClientOrderId` on a path that cannot transmit one, and teach the reconciler that a row with no broker-visible identifier cannot be resolved by `getOrderByClientId`: for such a row, reconcile by symbol and time window against `getOrders("closed")`, or preserve the position/orders payload the client already fetches at `client.ts:293-301` instead of reducing it to settle statuses. Restrict `provenAbsentAtBroker` to rows whose client id was actually submitted.

**Severity note.** Both refuters corrected high to medium. No wrong order is placed and the position views read live from Alpaca, so holdings are displayed truthfully. Also, `positions.closedOrders` fetches history from Alpaca rather than the local DB (`positions.ts:872-897`), so the real liquidation does appear in the Closed view; what is lost is FILLED status, executed price and time, the fill notification, and any ability to cancel or resolve the row.

## The `ALPACA_CLIENT_ORDER_ID_MAX_LENGTH = 48` question, resolved

Resolved. The constant is self-imposed, stricter than the documented broker limit by 80 characters, undocumented in the code, and load-bearing enough that it has already caused one bug on this branch.

Evidence gathered:

- `packages/alpaca/src/client.ts:32` declares `export const ALPACA_CLIENT_ORDER_ID_MAX_LENGTH = 48;` with no comment and no cited source. It is enforced at `client.ts:335-338` (`createOrderIdempotently` throws "client_order_id must be between 1 and 48 characters"), used to truncate at `client.ts:68-71` (`deriveClientOrderId`), and duplicated as a bare literal in two more places: `apps/api/src/lib/order-idempotency.ts:12` (a zod `.max()`) and `apps/web-v2/src/components/trade/order-idempotency.ts:1`.
- Alpaca's documented limit is **128**. I fetched `docs.alpaca.markets/reference/postorder` directly: `client_order_id` is "A unique identifier for the order. Automatically generated if not sent. (<= 128 characters)".
- The pinned SDK enforces nothing. In `@alpacahq/alpaca-trade-api@3.1.3`, `dist/resources/order.js` contains no length check, no `48`, no `128`; `client_order_id` appears only as a query parameter on the by-client-order-id lookup. The 48-character rejection is entirely the repo's own.
- **The cap is not inert.** `copy-mirror.ts:4203-4209` records the consequence in its own words: the logical mirror key `"copymirror:<follower>:<source>"` "is about 89 chars and createOrder rejects anything over ALPACA_CLIENT_ORDER_ID_MAX_LENGTH (48), so comparing against it alone could never match and this branch never fired." That is a real bug the branch had to fix: the crash-recovery scan that prevents a duplicate mirror order could never match. The 48 cap forced the broker-side id to be an opaque `rst-copy-<hash>` derived at `client.ts:38-54`, and `placeMirrorOrder` now has to compare against two id forms (`:4213-4216`) to cover mirrors placed before the bounded id existed.

Consequences of the divergence, in order of importance:

1. The broker-side identifier is a SHA-256 digest rather than the logical key, so an operator looking at an Alpaca order cannot tell which follower or which source item produced it without a database join. At 128 characters the logical key would fit whole with room to spare.
2. Every place that needs to correlate a broker order back to a mirror has to carry the hashed form plus a legacy fallback, which is the complexity that produced the never-firing recovery branch.
3. `deriveClientOrderId` silently truncates the base (`client.ts:71`) to fit the tail. At 48 characters the truncation budget is tight; at 128 it would not exist.

Recommended action: raise the constant to 128, keep the single source of truth in `packages/alpaca` and delete the duplicated literal in `apps/web-v2/src/components/trade/order-idempotency.ts`, and add a comment citing the vendor reference. Do **not** change the id **format** for orders already at the broker: the recovery paths that accept both forms must stay until no live `rst-copy-<hash>` orders remain. Raising the cap is safe on its own because Alpaca accepts anything up to 128 and the SDK validates nothing.

One caveat: this was not on the verified list and was not double-refuted. The facts above are directly observed, but the consequences (2) and (3) are analysis, not a demonstrated failure.

## Checked and found sound

Do not re-audit these. Each was pursued and either the code is correct or the claim was refuted on the merits.

- **`orders.broker_account_id` being NULL does not, by itself, let a mirror sell the wrong account's shares.** This was filed as a defect and refuted. The premises are all true (the column is NULL for every Alpaca order, `mirroredEquityExposure` buckets on `row.brokerAccountId?.trim().toLowerCase() ?? ""` at `copy-mirror.ts:3080`, the spans-accounts hold at `:3105-3112` needs `active.length > 1`), but persisting the identifier would not change the outcome by a single share in the scenario described: the exposure query selects only the mirror's own rows (`clientOrderId like copymirror:%`), so there is exactly one bucket either way, and routing reads `orders.broker_credential_id`, never the account key. The real consequence of the NULL column is finding 9 above, which is the opposite failure direction (a close that stalls rather than one that over-sells).
- **`deleteApiCredentials` is fail-safe.** `copy_trade_follows.credential_id` is `onDelete: "set null"`, so `decideFollowConsent` hits the empty-credential branch and skips. Only the UPDATE path (finding 3) is fail-open.
- **Closing an option through the trade ticket mirrors correctly.** `orders.ts:762` writes `SellToClose` with the underlying plus all three contract columns, and `mirroredEquityExposure` matches it (`copy-mirror.ts:3036-3065`). Finding 4 is specific to the Positions-panel Close button.
- **`clampSellToMirroredExposure` and `decideSellMirrorQty` are individually correct** (`copy-mirror.ts:877-885`, `:980-994`). Findings 6, 7 and 8 are all about poisoned or ambiguous **inputs** to those clamps, not the clamps themselves.
- **`done_for_day` mapping to SUBMITTED is correct** for GTC orders, which genuinely resume next session under the same id. Only `replaced` needs to change (finding 10).
- **The equity duplicate-recovery scan now fires.** `copy-mirror.ts:4203-4216` compares both the bounded `rst-copy-<hash>` and the legacy raw form; the never-matching version was fixed on this branch.
- **`positions.closedOrders` deliberately uses `nested=false`** (`positions.ts:892-896`) with a comment explaining why. That consumer is correct; `external-fill-sync` is not (finding 11).
- **The perp close-pairing deferral logic is sound** (`copy-mirror-close-pairing.ts:260-301`). Its problem is that the equity caller passes it nothing (finding 6).
- **`withRetry` preserves the error instance** (`packages/utils/src/utils/with-retry.ts:105-112`), so `response.status` survives to the classifier. The 403 misclassification is in the predicate, not in error propagation.
- **The pinned SDK is stock.** No `patchedDependencies`, no `patches/` directory, no axios interceptor. `bun.lock:231` pins `@alpacahq/alpaca-trade-api@3.1.3`, and the trading endpoints go through a bare `axios(req)` in `dist/api.js` with no `validateStatus` override, no internal 429 retry, and no entity mapping. Anything that looks like SDK normalization is not happening.

## Below the verification cap, reported honestly as unverified

Ten additional medium/low candidates were identified but did **not** go through the two-refuter process and are not defended here. Treat each as a lead, not a finding:

1. The copy-mirror resume recovers a possibly-placed order by scanning the last 500 broker orders instead of Alpaca's by-client-order-id endpoint.
2. Alpaca `suspended` is mapped to the terminal local status REJECTED, freezing a row for an order the broker may still work.
3. `done_for_day` is in `ExternalFillPoller`'s `TERMINAL_ALPACA_STATUSES`, so a GTC order's day-one partial may be published as a final fill and its next-day remainder lost.
4. Fractional sizing is hard-disabled (`isSymbolFractionable` returns false unconditionally), so a legal range of `usd`/`pct` follow settings may silently mirror nothing.
5. The equity close-pairing guard cannot see a paired open whose delivery already completed, so a same-window buy-then-sell may spend the exit.
6. A mirrored equity CLOSE may be terminally consumed rather than deferred when the follow's destination is a Hyperliquid credential.
7. The deferred-close backlog monitor is Hyperliquid-only, so an equity close wedged by credential rotation is invisible to operators.
8. An option close whose entry rule sizes to zero while mirrored exposure is zero may be thrown as `EAGAIN` forever, because closes are exempt from the attempt ceiling.
9. `ALPACA_CLIENT_ORDER_ID_MAX_LENGTH = 48` (resolved above, in its own section).
10. The deferred-close backlog report counts only perp closes, so an equity or option exit that now retries forever is invisible.

Items 7 and 10 are the same observation from two angles and are worth acting on together: several findings above (1, 9, and the `EAGAIN` tail of 2) end in a state that is only visible to an operator through a backlog report that does not cover equities.

## What this audit could not establish

Everything below needs a live Alpaca account (paper is sufficient for most of it) and could not be settled by reading code or docs.

- **Whether Alpaca accepts `position_intent` on a plain equity order, and what it does with a conflicting one.** The `CreateOrderRequest` schema carries the field and one public issue reports a 422 `40010001` "position intent mismatch" on an equity order, but I could not confirm the behaviour first-hand. Finding 7's recommended fix depends on it: if Alpaca ignores the field on equities, the pre-BUY position read is the whole fix.
- **Whether Alpaca accepts GTC on an option limit order at all.** `packages/alpaca/src/time-in-force.ts:62-67` asserts it does, and a probe script (`scripts/probe-alpaca-option-gtc.ts`) exists in the repo, but I did not run it. If GTC is rejected, finding 15's failure changes shape (the exit dies immediately rather than resting) without becoming safe.
- **The actual deviation between the indicative and OPRA option quote for a given contract.** Alpaca documents that indicative quotes are "not actual OPRA quotes", but neither direction nor magnitude. Finding 15 does not depend on this (a limit resting exactly at the touch is documented as possibly non-marketable regardless), but sizing the harm does.
- **Whether re-POSTing a duplicate `client_order_id` for an order that is no longer active is accepted or 422s.** Alpaca's error guide scopes the "client_order_id must be unique" 422 to another **active** order. Finding 1's fix (retry the same deterministic id) is safe under that reading, but the exact semantics for a settled id are undocumented and untested here.
- **Exactly which fields Alpaca omits on an `mleg` parent in a live `GET /v2/orders?nested=true` response.** The docs and the SDK model agree that symbol, side, asset_class and asset_id are omitted, but I did not observe a real mleg payload. Finding 12's specific failure (23502 on `orders.symbol`) follows from the omission; if Alpaca instead sends a synthesized top-level symbol, the outcome becomes a corrupted row rather than a wedged cursor.
- **Whether a 207 element with a non-200 status still carries a `body`.** The schema marks `body` optional. Finding 5's fix should not assume it is present on failed elements.
- **Real rate-limit behaviour under a multi-follower poll cycle.** The 200/min limit is per account and each follower supplies their own credential, so 429 pressure comes from one follower's own traffic (mirror sizing plus `OrderSyncPoller` plus `ExternalFillPoller` plus the API surface). Whether that actually crosses 200/min at the open is a measurement, not a read.
